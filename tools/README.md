# tools/ — instruments of the CoreLR project

Layout: `analysis/` (size, stack, cycles), `bench/` (talk to the machine, check GCode, hash the step stream), `generators/` (write committed artefacts),
`prototypes/` (experiments kept for the record), `lib/` (reads `local.conf`: `corelr_env.sh`, `corelr_env.py`), and at this level `mutate.py`, `check_help.sh`, `check_links.py`.
The host test suite lives in [`tests/host/`](../tests/host/README.md), the mutants in `tests/mutation/`.

Everything used to **measure** the firmware rather than build it. One rule: **every tool answers `-h` / `--help`** (usage,
options, examples, exit status), and `tools/check_help.sh` checks it. Tools write only to a temporary directory or their own
`out/` (git-ignored), never to the sources.

The standing method behind them: *measure, never assume; and a test that cannot fail proves nothing* — so there is a tool for
the size, one for the time, one for the stack, and one that breaks the code on purpose to see whether the tests notice.

## Where the flash, the RAM and the stack go
| Tool | What it answers | Typical use |
|---|---|---|
| [`build_size.sh`](analysis/build_size.sh) | Does it fit the Nano (30 720 bytes of flash, **not** the Uno's 32 256)? Builds ONE variant with the project's CMake build (`-v serial\|sd`, `-D` defines, `-C` without `-mcall-prologues`) and prints flash, RAM, free. Keeps the build and its ELF. | `tools/analysis/build_size.sh -v sd -D CORELR_MATH=CORELR_MATH_64` |
| [`check_export_ino.sh`](analysis/check_export_ino.sh) | Does the sketch **exported for the IDE** (`export_ino` target) build, with the flags of its `platform.local.txt`, to the same image as CMake? And does the SD export without them stop at the `#error`? | `tools/analysis/check_export_ino.sh` |
| [`compare_with_ide.sh`](analysis/compare_with_ide.sh) | Is the CMake build the **same firmware** as the Arduino IDE's? Builds both variants both ways and compares the `.hex` byte for byte (`ide_build.sh` is the reference build). Run it after touching `cmake/`, `third_party/` or the compiler. | `tools/analysis/compare_with_ide.sh` |
| [`check_image_symbols.py`](analysis/check_image_symbols.py) | **Does an image hold anything of the OTHER image?** Reads each linked image's map file and `avr-nm` symbols against `cmake/variant_modules.txt` (SDReader, sdfat, SPI for `sd`; Uart, SerialLink for `serial`): an object file or a symbol of the other image is a violation. Found nothing in the images since 2026-10-27; on the build before that day it finds the 86 bytes of dead SD library code the serial image carried. Also the CMake target `check_image_symbols`. | `cmake --build --preset avr-default && tools/analysis/check_image_symbols.py -v` |
| [`fn_sizes.py`](analysis/fn_sizes.py) | Code size per function; or the **delta between two ELFs**, to see where a change's bytes went. | `fn_sizes.py before.elf after.elf` |
| [`line_sizes.py`](analysis/line_sizes.py) | Bytes per **source line** (inlined code charged to its origin): how the duplicated `L`/`R` blocks and the helper inlined seven times were found (−656 bytes of trims). | `line_sizes.py build/grbl_corelr.ino.elf --file Motion.c` |
| *(`HOST_CFLAGS=-fshort-enums tests/host/run_all.sh` runs the host suite with extra compiler flags.)* | |
| [`stack_depth.py`](analysis/stack_depth.py) | Worst-case stack depth per call chain, from `avr-objdump -d` of the linked ELF (needs the interrupt roots too). | `stack_depth.py dis.txt main __vector_11 __vector_7 __vector_8` |

| [`flag_sweep.sh`](analysis/flag_sweep.sh) | **Which compiler/linker flag shrinks the image?** One build per candidate flag (29 built in), against the baseline: flash and RAM. Alone only -- the combination is `flag_truth_table.py`'s. | `flag_sweep.sh -v sd -c relax` |
| [`flag_truth_table.py`](analysis/flag_truth_table.py) | **The size flags as a truth table**: builds EVERY combination of the flags of `cmake/size_flags.txt` (2^N builds, `-j` at a time), prints flash/RAM for each, and per flag what it brings alone, with all the others, and on average -- and which one HURTS in combination. **To be redone before each release.** Reports: `docs/design-notes/SizeFlags-TruthTable-*.md`. | `flag_truth_table.py -v sd -j 8 --md report.md` |


## The mechanics
| Tool | What it answers | Typical use |
|---|---|---|

## Behaviour — are the tests worth anything?
| Tool | What it answers |
|---|---|
| [`tests/host/`](../tests/host/README.md) | The host test suite: the real firmware modules on the PC against a stub of everything else, ten tests (arcs, parser, motion, arithmetic, LCD driver and UI against a bus model…). `run_all.sh [CORELR_MATH_48\|_64]` runs all; `run_test.sh TEST` one. Both arithmetics must pass. |
| [`mutate.py`](mutate.py) | **Mutation testing**: break the code on purpose, in a copy, and say whether a chosen test noticed (CAUGHT / NOT CAUGHT / INVALID). A crash counts as caught. `--script` runs another test than a host test (e.g. `tests/cmake/test_check_size.sh` for `cmake/CheckSize.cmake`). Batches of known mutants are in [`tests/mutation/mutants/`](../tests/mutation/mutants/). |
| [`check_mutants_union.py`](check_mutants_union.py) | Reads the outputs of the runs of ONE mutant batch (one per test) and says whether every mutant is killed by **at least one** of them: gaps, `EQUIVALENT` mutants, and the outputs that cannot be trusted (empty, unfinished, different batches) are told apart. Exit 0 / 1 gap / 2 bad input. Tested by `tests/tools/test_check_mutants_union.py`, mutants in `union_checker.txt`. |
| [`mutation_ci.sh`](mutation_ci.sh) | Runs the mutant batches **as the CI's `mutation` job does** and judges each by the union of its runs (`-l` lists the groups, `-o DIR` keeps the outputs). The only way a mutation run fails the CI. |
| [`release_package.sh`](release_package.sh) | Collects what a **release** carries from a finished build: per image the `.hex`, `.elf`, `.map`, the IDE export and the API zip, plus `build-info.txt` (commit, compiler, flags, sizes) and `SHA256SUMS`; refuses an `.eep`. Run by `.github/workflows/release.yml`. | `tools/release_package.sh -v <version>` |
| [`tests/tools/test_mutant_batches.py`](../tests/tools/test_mutant_batches.py) | A static check of **every** mutant of every batch (a second, no build): four fields, the file exists, `old` occurs exactly once, no twin names. The mutants that already cannot run are listed in `tests/mutation/stale_mutants.txt`; the list can only shrink. Part of `ctest`. Tested by `test_mutant_batch_checker.py`, mutants in `batch_checker.txt`. |
| [`gen_serial_tests.py`](generators/gen_serial_tests.py) | Writes `tests/bench/gcode_serial/` for a machine given as `--geometry D,L` (the calibration's motor distance and cable length): what the serial link accepts (words, arcs and their direction, `G92`/`G10`, pen words, `M2`/`M30`, comments, 80-character lines), one file per refusal with the `error:N` it must give, and a drawing in the two pen styles. Checked by `tests/host/check_serial_files.sh` (part of `run_all.sh`), with `gcode_check.sh --serial`. |
| [`gen_gcode.py`](generators/gen_gcode.py) | Writes the GCode files to print on the machine, `tests/bench/gcode/*.gc` (a command test, a 200 mm square, a circle R=100, a test card), each starting with the pen up and a return to the origin. |
| [`gen_sd_tree.py`](generators/gen_sd_tree.py) | Writes `TREE/` on the SD card for the browser: levels 1 to 4 with 8-character names (the 4th must be **refused**: the path would be 32 bytes), a directory of 40 files and 3 sub-directories at level 2 and one of 35 files at level 3 (the deepest stack). Tiny square files of different sizes, so that the one started is recognised. |
| [`gen_jogcurve.py`](generators/gen_jogcurve.py) | Writes `firmware/src/JogCurveTable.h`, the optional table (`JOGCURVE_USE_TABLE=1`) for the shape of the Control jog's speed response (`-e 2` quadratic, `-e 1.5` gentler at the top); `--check` is part of `run_all.sh`. |
| [`gen_tension_chart.py`](generators/gen_tension_chart.py) | **How hard does each cable pull?** Tables, an SVG (maps of the two tensions and curves) and a CSV of the cable tensions, in multiples of the pen's weight, for a geometry (`-D` motor distance, the margins, `--mass-g`): what the top margin costs. Statics in `docs/hardware/CableTension.md`. | `gen_tension_chart.py -D 1000 --svg /tmp/t.svg` |
| [`gen_geometry_svg.py`](generators/gen_geometry_svg.py) | Draws `docs/hardware/images/Geometry.svg`: the dimensions to measure (D, Lref, H), the two coordinate frames, the calibration steps, the cable lengths in the test square, and what the model assumes. `--verify` checks every figure against the firmware's real `Calibration.c` and `Motion.c` (`tests/host/geometry_probe.c`). |
| [`gen_branding_png.py`](generators/gen_branding_png.py) | Renders the PNG files of `docs/branding/` (logo, favicon, wordmark, social preview, machine icon and schematic) **from their SVG sources** with librsvg, at the widths of its table; nothing is redrawn by hand. Checked 2026-10-31: pixel-identical to the first four PNGs, which had been made by hand with cairo. `-l` lists the table; names render only those. Needs `python3-gi` and `gir1.2-rsvg-2.0`. | `gen_branding_png.py machine-schematic.png` |
| [`gen_wiring.py`](generators/gen_wiring.py) | Draws the **wiring diagrams** (`docs/hardware/images/wiring/*.svg`) in the Arduino/Fritzing breadboard style: the vendored Fritzing parts (`third_party/fritzing-parts/`, embedded unmodified) placed in a scene, wires from pin to pin by name (`D13`, `GND#2`…). Each SVG carries its CC BY-SA 3.0 credit in its metadata. `--list`, `--all`, `gen_wiring.py overview`. **The pins are read from `firmware/config/HwConfig.h` and, for the fixed SPI/TWI pins, from the vendored Arduino core's `pins_arduino.h`: change a pin, regenerate, the wires move.** **`--verify`** checks every wire of every diagram against the same sources (the nets: each signal, the +5 V, the ground; a short or an open net is reported). Tested by `tests/tools/test_wiring.py`, proved able to fail by `tests/mutation/mutants/wiring.txt` (44 mutants, all caught). |
| [`gcode_check.sh`](bench/gcode_check.sh) | **What would the machine do with this GCode file?** Runs it through the firmware's real parser, planner and generator on the host: refused lines (with grbl's error number), the box actually traversed and drawn, ink length, starts/ends pen up at the origin, lines too long for the SD (47) or the link (80). `--svg DIR` draws the path. |
| [`stream_hash.sh`](bench/stream_hash.sh) | Is a refactor of `Motion` **behaviour-neutral**? Compares the hash of every step entry sent to `Stepper` (820 385 and 11 421 789 entries) at a git ref and in the working tree. The standard every flash trim is held to. `-C MIRROR_Y` feeds the working tree the mirror image of every scenario (`tests/host/mirror_y.h`), to prove the Y flip changed only the sign. |
| [`serial_probe.py`](bench/serial_probe.py) | **Drives the real machine over the serial link** and logs every byte with its time: `status` (moves nothing), `ring` (the EEPROM position ring: move, wait 3 s, close the port, reopen, check the position, N times), `pause-resume`, `cancel-after-pause`, `abort` (Candle's Abort: Ctrl-X during a move, then its three restoration lines in one burst; checks every reply `ok`, Idle, and the head back on the position Candle had read) (small ±40 mm moves along X, pen never touched). Found the frozen resume of 2026-10-10 (with `CORELR_DEBUG_JOBSTATE=1`, whose `|D:job,motion,stepper,queued,K,N>` field it prints). **Moves the machine; read its `-h` first.** |
| [`candle_spy.py`](bench/candle_spy.py) | **A fake grbl machine on a pseudo-terminal** (no real machine): logs every line Candle sends and every reply, with a grbl-faithful `?` report (`MPos`, periodic `WCO`), `$#` with `[G92:..]`, `$H`, G92/G10/G53/G91/`$J=`. Used to learn what Home / Safe position / Restore origin / Zero XY send. Its `-h` says how to point Candle at it. |
| [`check_halt_order.py`](analysis/check_halt_order.py) | Does the sketch close Stepper's gate only **after** the halt ramp is enqueued? (the one rule of `grbl_corelr.ino` no host test can run; bench 2026-10-10: a pause that never finished). Part of `run_all.sh`. |
| [`req_refs.py`](analysis/req_refs.py) | **Do the code and the documentation cite the requirements correctly?** Each requirement heading has an invisible anchor, `<a id="REQ-..."></a>`, and a comment that Doxygen reads cites it as `@req{REQ-...}` (a link); an ordinary comment keeps the plain identifier. Fails (exit status = the number of problems) on a heading without its anchor, a citation that names no requirement, a plain identifier in a Doxygen comment or page, a range or shorthand (`-0001, -0006`), an `@req{}` where Doxygen does not read, a citation on a title line, a citation in a requirement file that names nothing, a Doxygen command with its backslash in a requirement file, a protocol item (`FW-03`, `P7`, a section) that is plain in a Doxygen comment, unknown, or with a wrong label, the path of a document that is a page (`docs/protocol/EepromLayout.md`) in plain text in a Doxygen comment, a wrong or misplaced applicability tag (`*Applies to: serial image only*`), a requirement of a module that `cmake/variant_modules.txt` gives to one image without that image's tag. `--add-anchors` writes the anchors of new requirements, `--convert` rewrites plain citations as `@req{}`, `--filter FILE` (with `--image`, the image Doxygen documents, and `--applies`) is the **input filter** through which Doxygen reads the requirement files and the protocol (page id, heading labels, links between requirements, pictures of `docs/hardware/images` found by their name so that they are copied, labels and anchors for the protocol's items (`--protocol`), `file:line` not taken for a URL; the files stay plain on GitHub). Run by `ctest` (`req_refs`); tested by `tests/tools/test_req_refs.py` (196 mutants). |
| [`check_version.py`](analysis/check_version.py) | **What is the software version, and is it the tag's?** The version is written once, in `firmware/config/Version.h` (three numbers and a suffix, `-dev` between two releases); this tool reads that file as text and prints the version string. `--tag TAG` (the `release` workflow) fails unless the suffix is empty and the tag is `v` + the numbers; `--release` fails on a development version; `--cmake VERSION` fails unless CMake read the same; `--sources` fails if the version is written anywhere else (a literal in `CMakeLists.txt` or `cmake/`, a version-like string in `firmware/`). No git hash: the `.hex` files are compared byte for byte. Tested by `tests/tools/test_check_version.py` (`tests/mutation/mutants/check_version.txt`, all caught). | `check_version.py --tag v1.0.0 --sources` |
| [`doc_warnings.py`](analysis/doc_warnings.py) | **What did Doxygen complain about, module by module?** Sorts the warning log of one documentation of the `doc` target (`build/doxygen/serial/doxygen-warnings.log`, or `sd/`) into *markup* (a comment Doxygen could not read: an error), *undocumented* and *incomplete* `@param` lists (gaps), *no dot* (diagrams skipped for want of Graphviz) and *external* (anything in `third_party/`: not ours, never an error), and prints a table per module; `--list CLASS` shows them, `--check` exits with the number of markup warnings; `--gaps` prints the inventory kept in `docs/doxygen/gaps_*.txt` and `--baseline FILE` compares a log with it (a new gap, or a fixed one still listed, fails: `REQ-CoreLR-D-Build-0017`). Run by the `doc` target; tested by `tests/tools/test_doxygen.py` (`tests/mutation/mutants/doxygen.txt`, all caught). |
| [`check_links.py`](check_links.py) | Do the relative links of every Markdown file point at something, and does no file still name the retired layout? Run it after moving or renaming a document. |
| [`hypot_bound.sh`](prototypes/hypot_bound.sh) | The numerical bound `CORELR_MATH_48`'s `Motion_Hypot` stands on: worst true residual over adversarial inputs (must be < 2^32; measured 0.85 × 2^32). |

## Experiments kept for the record (not tools)
Prototypes whose result decided a design; each has its own README with the numbers so they are not redone.
[`arcproto/`](prototypes/arcproto/README.md) — CORDIC against the polynomial for arcs; [`evproto/`](prototypes/evproto/) — the step-event generator before it was ported;

## Conventions for a new tool
1. It answers `-h`/`--help` and says what it is for, its options, an example and its exit status.
2. It takes paths from its arguments or from its own location, never from a hard-coded home directory; the toolchain
   location is an environment variable with a default (`ARDUINO_ROOT`, `AVR_BIN`).
3. It never edits the sources; anything it must change, it changes in a **copy**.
4. It is added to `check_help.sh` and to the table above.
5. A **result worth keeping goes into a requirement** (`requirements/`), with the command that produced it — a tool is how a
   number is reproduced, not where it is recorded.

## Toolchain and local settings
`avr-gcc 7.3.0` (with `avr-nm`, `avr-objdump`, `avr-size`, `avrdude`), CMake ≥ 3.20 and Ninja, host `gcc`/`g++` with `-m32`, Python 3; the Arduino IDE 1.8.x only for the **reference** build of `compare_with_ide.sh`.
**Where they are is the machine's business**: `local.conf` at the repository root (copy `local.conf.example`; git-ignored) — read by CMake, by the shell tools (`lib/corelr_env.sh`) and by the Python tools
(`lib/corelr_env.py`); the environment overrides it, auto-detection (PATH, then an IDE installation) completes it. A tool never hard-codes a path.
