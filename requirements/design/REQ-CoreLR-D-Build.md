# Design Requirements — Build

Module: **Build** — the CMake + Ninja build of the firmware (`CMakeLists.txt`, `CMakePresets.json`, `cmake/`, `firmware/CMakeLists.txt`, `third_party/CMakeLists.txt`),
its local-settings file and its checks.

Realizes: [`REQ-CoreLR-F-Build-0001`..`0006`](../functional/REQ-CoreLR-F-Build.md) (`-0013`, the API documentation, realizes none: it is bound by `-0002` and `-0004`)

Origin: maintainer decision, 2026-10-10 (leave the Arduino IDE, which hides the compiler flags) and 2026-10-11 (tool paths in a separate file; VS Code). Recommendations accepted
2026-10-11: vendor the Arduino core, keep the `.ino`, upload by `avrdude`, prove the image identical to the IDE's.
Status: Implemented (2026-10-11), host- and toolchain-verified; **never flashed from this build** (the images are byte-identical to the IDE's, which were).

## REQ-CoreLR-D-Build-0001 — Generator, toolchain file, presets
<a id="REQ-CoreLR-D-Build-0001"></a>
CMake ≥ 3.20 with the Ninja generator. The AVR toolchain is described by `cmake/avr-gcc.cmake` (a toolchain file: `avr-gcc`, `avr-g++`, `avr-gcc-ar` — the
wrapper that loads the LTO plugin —, `avr-objcopy`, `avr-size`). `CMakePresets.json` carries the everyday commands: `avr-default` (both variants, 48-bit
arithmetic), `avr-math64`, `avr-debug` (`CORELR_DEBUG_JOBSTATE`), and `host` (the native tests, no AVR toolchain). The build type is not used: CMake's per-type default
flags are emptied in the toolchain file, because the flags are the project's own (-0003).

## REQ-CoreLR-D-Build-0002 — One target per variant
<a id="REQ-CoreLR-D-Build-0002"></a>
`corelr_serial` and `corelr_sd` (`cmake/Firmware.cmake`, `corelr_add_variant()`), both built by `all`. Each is a complete build — Arduino core archive, sketch
modules, the `.ino`, vendored sdfat, SPI — because the compile settings reach every file, core included (`-mcall-prologues` changes the core's code too). The
job source (`CORELR_JOB_SOURCE`), the arithmetic (`CORELR_MATH`) and the debug switches are definitions on every file; `CORELR_EXTRA_DEFS` adds others for experiments
(every selector in `SwConfig.h` is `#ifndef`-guarded). Outputs per target: `corelr_<v>.hex` (`objcopy -O ihex -R .eeprom`: **never an `.eep`**), `corelr_<v>.map`,
`firmware/corelr_<v>.elf`.

## REQ-CoreLR-D-Build-0003 — The IDE's flags, recorded
<a id="REQ-CoreLR-D-Build-0003"></a>
Taken from `arduino-builder -verbose` for `arduino:avr:nano:cpu=atmega328`, and kept in `cmake/Firmware.cmake`:
C `-g -Os -w -std=gnu11 -ffunction-sections -fdata-sections -flto -fno-fat-lto-objects`; C++ `-std=gnu++11 -fpermissive -fno-exceptions -fno-threadsafe-statics -Wno-error=narrowing`
(plus the C ones, minus `-fno-fat-lto-objects`); `-mmcu=atmega328p -DF_CPU=16000000L -DARDUINO=10600 -DARDUINO_AVR_NANO -DARDUINO_ARCH_AVR`; link
`-w -Os -g -flto -fuse-linker-plugin -Wl,--gc-sections -lm`, linked with the C driver; **plus the size flags of REQ-CoreLR-D-Build-0012** (compile and link, the same list for the IDE reference build). `-mcall-prologues` is an option (`CORELR_CALL_PROLOGUES`, ON): the SD variant does not link
without it (31 058 bytes against 29 608). Link order — sketch modules (alphabetical), `.ino`, sdfat, SPI, core archive, in the core archive's own order — is the IDE's, because it
fixes the layout of the image. The project's own sources add `-Wall -Wextra` (`CORELR_WARNINGS`), which changes no code; the build is warning-free.

## REQ-CoreLR-D-Build-0004 — Size limits enforced
<a id="REQ-CoreLR-D-Build-0004"></a>
`cmake/CheckSize.cmake` runs after every link with the IDE's arithmetic (flash = `.text`+`.data`; static RAM = `.data`+`.bss`+`.noinit`) and fails the build over `CORELR_FLASH_BYTES` (30 720) or
`CORELR_RAM_BYTES` (2 048), printing the figures otherwise. The worst-case **stack** is not known at link time: `tools/analysis/stack_depth.py` measures it from the ELF.
Tested by `tests/cmake/test_check_size.sh` (a fake `avr-size`; boundaries, each section, the limits), which was put through `tools/mutate.py`: `tests/mutation/mutants/checksize.txt`, 15 mutants, all caught.

## REQ-CoreLR-D-Build-0005 — Proven identical to the IDE's image
<a id="REQ-CoreLR-D-Build-0005"></a>
`tools/analysis/compare_with_ide.sh` builds both variants with CMake and with the real `arduino-builder` (reference build `tools/analysis/ide_build.sh`) under the same settings and compares the `.hex`
byte for byte. Measured 2026-10-11, **identical** for serial and sd, in the default settings and with `CORELR_MATH=64` + `CORELR_DEBUG_MISS_COUNT=1`
(29 608 / 26 474 bytes of flash by default, as before the move). Run it after touching `cmake/`, `third_party/` or the compiler.

## REQ-CoreLR-D-Build-0006 — Vendored core, the `.ino` kept
<a id="REQ-CoreLR-D-Build-0006"></a>
`third_party/arduino-core/` holds Arduino AVR core 1.8.8 verbatim (`cores/arduino`, the Nano's variant pins and the `standard` pins they include, the SPI library `sdfat` includes), with a
`PROVENANCE.md` and an `md5` manifest; vendored whole rather than trimmed, so the claim "byte-identical to upstream" stays checkable (LGPL 2.1; `THIRD_PARTY.md`). The sketch
`firmware/app/grbl_corelr.ino` is unchanged: CMake compiles it as C++ through a generated file that puts `#include <Arduino.h>` in front (what the IDE does; its prototype generator is not
needed, the file defines before it uses). Consequence: the sketch no longer opens in the IDE as such (the firmware is split into `app/`, `src/`, `config/`).

## REQ-CoreLR-D-Build-0007 — Machine-specific settings: `local.conf`
<a id="REQ-CoreLR-D-Build-0007"></a>
Paths of the toolchain and the board live in `local.conf` at the repository root (git-ignored; template `local.conf.example`), `KEY=VALUE` lines read by **three** consumers with the same rule —
environment / `-D` first, then the file, then auto-detection (PATH, then an Arduino IDE 1.8.x installation): `cmake/LocalConf.cmake`, `tools/lib/corelr_env.sh`, `tools/lib/corelr_env.py`.
Keys: `AVR_BIN`, `AVRDUDE_CONF`, `CORELR_PORT`, `CORELR_BAUD`, and `ARDUINO_ROOT`/`ARDUINO_PKGS`/`ARDUINO_LIBS` for the reference build only. No tool contains a user's path any more. The compiler
version is checked (`CORELR_EXPECTED_GCC`, 7.3.0): another one warns, since every recorded size is that compiler's.

## REQ-CoreLR-D-Build-0008 — Upload
<a id="REQ-CoreLR-D-Build-0008"></a>
`upload_serial`, `upload_sd`: `avrdude -p m328p -c arduino -P $CORELR_PORT -b $CORELR_BAUD -D -U flash:w:<hex>:i`; never part of `all`. Default 115200 baud (the fqbn `arduino:avr:nano:cpu=atmega328`;
57600 for an "old bootloader" Nano). **Flashing resets the board and a reset before the position is stored (2 s of stillness) loses the calibration**: only on the maintainer's say-so, and the VS Code tasks ask first.
*Not yet tried on the board.*

## REQ-CoreLR-D-Build-0009 — Editor
<a id="REQ-CoreLR-D-Build-0009"></a>
`.vscode/` is versioned for `extensions.json` (CMake Tools, C/C++, Python, EditorConfig), `settings.json` (presets always, IntelliSense from CMake Tools' `compile_commands.json`) and `tasks.json`
(build, host tests, size report, compare with the IDE, tool/link checks, and the two flash tasks behind a confirmation); the rest of `.vscode/` is ignored. No debugger configuration: there is no hardware debugger
on the board.

## REQ-CoreLR-D-Build-0010 — The flag is checked; an IDE sketch can be exported
<a id="REQ-CoreLR-D-Build-0010"></a>
**Check.** avr-gcc defines **no macro** for `-mcall-prologues` (measured: `-dM -E` output identical with and without), so the build announces it: CMake defines `CORELR_CALL_PROLOGUES=1` together with the flag (as
does `ide_build.sh`, and the generated `platform.local.txt`), and `grbl_corelr.ino` ends in an `#error` that names the cause when an **AVR** build of the **SD** variant lacks it (31 058 bytes without, 29 608 with,
limit 30 720), instead of an anonymous "sketch too big". Host builds are not checked. Limit of the check: it trusts the announcement, it cannot see the flag.
**Export.** `cmake --build build/avr-default --target export_ino` (or `export_ino_serial`, `export_ino_sd`) runs `cmake/ExportIno.cmake` and writes, under `build/avr-default/ide_sketch/<variant>/`, a flat
`grbl_corelr` sketch folder (the `.ino`, every module, `config`, vendored sdfat under `src/` with its one include patched), the variant selected as the default of `CORELR_JOB_SOURCE` in the copy of
`SwConfig.h`, a `platform.local.txt` (`-mcall-prologues -DCORELR_CALL_PROLOGUES=1`, to copy next to the AVR core's `platform.txt`) and a `README.txt`. **Generated, in `build/`, never committed.**
`tools/analysis/check_export_ino.sh` builds both exports with the real `arduino-builder` under the flags of that file: the `.hex` is **identical** to CMake's for both variants (2026-10-11), and the SD export
without the flags stops at the `#error`. The IDE remains a convenience, not the reference.

## REQ-CoreLR-D-Build-0011 — The bring-up sketches are CMake targets (implemented 2026-10-11)
<a id="REQ-CoreLR-D-Build-0011"></a>
`tests/bench/CMakeLists.txt` -> `corelr_bench_libraries()` (the firmware's modules once, as an **object** library whose objects are all linked -- an archive would drop a module that only defines an interrupt vector --, and the Arduino core once, as an archive, both with the
SD variant's settings) and `corelr_add_bench(<name> <sketch.ino> [STANDALONE])` per sketch: `bench_<name>` (.elf/.hex/.map, the same size check), `upload_bench_<name>`; the target `bench` builds them all and is **not** part of `all`. T01 (I2C scan with the raw TWI registers, the
firmware's `LcdI2c`, no `Wire`/`LiquidCrystal_PCF8574`), T02 (start-up bisection, the order of `setup()`), T05 (phase check) are in `bench`; T03 (the real `grbl_corelr.ino` with a stack painter and a hexadecimal UART report) is **`STANDALONE`**, outside `bench`: it fitted after the size flags (-0012) but the SD image has grown, and T03 is 82 bytes too large for the Nano (30 802 of 30 720; the first CI run caught it, 2026-10-26). It is built by naming it, once the image or the painter shrinks; the SD stack is measured statically by `tools/analysis/stack_depth.py` meanwhile. T04 was removed.
Built, **not run on the board** in this form; they have no host test (they exercise the hardware), so there is nothing to put through mutation testing.

## REQ-CoreLR-D-Build-0012 — The size flags (adopted 2026-10-11, to be re-evaluated before the first release)
<a id="REQ-CoreLR-D-Build-0012"></a>
Question (maintainer): are there equivalents of `-Os`? Answer: **`-Os` is the smallest level avr-gcc 7.3 has** (`-Oz` is refused: only `0 1 2 3 s g fast`; `-O2` costs +3 534 bytes, `-Og` +6 834). What exists is individual flags that change what `-Os` does.
**Measured one at a time** (`tools/analysis/flag_sweep.sh`; `build_size.sh -F/-L`; 29 candidates; SD, 30 546 bytes): `-fno-gcse` -440, `-mrelax` (compile **and** link) -378, `-fshort-enums` -348 (RAM -5), `-fira-algorithm=priority` -224, `-fno-inline-small-functions` -122,
`-mstrict-X` -120, `-fno-guess-branch-probability` -54; `-fno-jump-tables` +30, `-fno-tree-pre` +62, `-fno-split-wide-types` +154, `-fno-peephole2` +214, `-fno-ipa-cp` +958. No effect: `-flto-partition=one/none`, `-fwhole-program`, `-maccumulate-args`, `-fno-inline-functions-called-once`,
`-fno-caller-saves`, `-fconserve-stack`, `-fmerge-all-constants`, `-fno-ident`, `-fno-rtti`, `-fno-use-cxa-atexit`, `-fno-ipa-icf`, `-fno-reorder-functions`. `-mmain-is-OS_task` does not build here.
**Then as a truth table** (`tools/analysis/flag_truth_table.py`: all 2^7 = 128 combinations of the seven candidates, per variant; reports `docs/design-notes/SizeFlags-TruthTable-sd.md` and `-serial.md`). The gains do not add up, and the table found what the one-at-a-time sweep could not:
**`-fno-guess-branch-probability`, -54 bytes alone, makes the image BIGGER in the presence of the others (+102 bytes SD, +80 serial): dropped.** `-fno-inline-small-functions` is nearly neutral in combination (+16 SD with all the others, -12 alone on serial). The best subset of the six without enums, for both variants:
`-mrelax -fno-gcse -fira-algorithm=priority -mstrict-X -fno-inline-small-functions`.
**Adopted**: `cmake/size_flags.txt` is the one list (read by CMake -- `CORELR_SIZE_FLAGS`, ON --, by `ide_build.sh`, by `ExportIno.cmake` for `platform.local.txt`, and by the truth-table tool): those five, `on`; `-fshort-enums` and `-fno-guess-branch-probability` stay `off` there
(`CORELR_SHORT_ENUMS`, default OFF: -376 bytes more and 6 bytes of RAM, but it changes the size of every enum; audited: none is in an EEPROM image or a packed record, only 9 enum types, states and parameters). Result, Nano: **SD 30 546 -> 29 208 (-1 338; 1 512 bytes free instead of 174), serial 27 424 -> 26 626 (-798)**;
the images stay byte-identical between the CMake build and `arduino-builder` given the same list (`compare_with_ide.sh`; `-S` and `-E` reproduce the images without the size flags and with the enums), and the exported IDE sketch builds to the same image through its `platform.local.txt` (`check_export_ino.sh` reads that file itself).
Costs, measured: `Motion` alone on a 30 mm line 2 374 349 -> 2 454 318 cycles (**+3.4 %**, 10.1 -> 10.4 % of the CPU), an arc 12.1 -> 12.4 %; worst stack SD 321 -> 334 (margin 370), serial 317 -> 314. Not measured: the ISRs on the simulator (the harness hangs). **Host-verified only**: the host tests are native builds and do not exercise this code;
the machine has not run an image built with these flags. `bench_T03_StackWatch` fits now (it was 94 bytes over) and is part of `bench`.
**Revised 2026-10-12 (maintainer: the flash comes first, unless stack, CPU or RAM object), per variant.** The truth tables were redone on the code of 2026-10-12 (`SizeFlags-TruthTable-sd.md`, `-serial.md`) and showed that the two variants do not want the same set: `-fno-gcse` is -538 B on SD but **+104 B on serial**; `-fshort-enums` is the best remaining flag in both (-374 B SD, -240 B serial, RAM -5 / -3, and it hurts neither). `cmake/size_flags.txt` therefore has a status per variant: `on` (both), `sd`, `serial`, `off`; `short_enums` is now `on`, `no_gcse` is `sd`. The best subset of each table is what is applied: **SD = relax, no_gcse, ira_priority, strict_x, no_inline_small, short_enums: 30 152 -> 29 778 B (942 free); serial = relax, ira_priority, strict_x, no_inline_small, short_enums: 29 062 -> 28 750 B (1 970 free)**, exactly the tables' predictions. (`-fno-inline-small-functions` looked harmful in the all-on row, but that row carries `-fno-guess-branch-probability`; in the chosen set dropping it costs +120 B on SD, so it stays.) Costs, measured: worst stack SD 334 -> **334**, serial 412 -> **405**; RAM SD 1 345 -> 1 340, serial 939 -> 936; cycles (`cyclesim`) Motion on a 30 mm line 3 072 per entry unchanged (SD), 3 072 -> 3 079 (serial, +0.2 %), an arc 12.4 % in both, `SerialLink_Task()` passes within +-0.5 %, the UART interrupts unchanged. The host suite also passes with `-fshort-enums` (`HOST_CFLAGS=-fshort-enums tests/host/run_all.sh`). The CMake and IDE builds stay byte-identical (`compare_with_ide.sh`). On the machine (serial image): `serial_probe.py` `jog` (22 checks), `ring` (4 cycles), `abort`, `pause-resume` all passed.
**Re-evaluated 2026-10-26, before the first release (maintainer's rule: before V1, and before any later release if the compiler, the core or the code changed much): no change.** `flag_truth_table.py` was run again on the code of 2026-10-26, both variants, all 2^7 = 128 combinations each, none FAILED (`SizeFlags-TruthTable-V1-sd.md`, `-V1-serial.md`; the tables of 2026-10-12 are kept for comparison). The best subset of each table **is the set already applied**, and it is the global minimum: **SD = relax, no_gcse, ira_priority, strict_x, no_inline_small, short_enums: 30 524 B (196 free); serial = relax, ira_priority, strict_x, no_inline_small, short_enums: 28 852 B (1 868 free)**, equal to the images the build produces. Dropping any one flag of the set from the adopted set costs, SD: ira_priority +274, no_gcse +556, no_inline_small +72, relax +376, short_enums +380, strict_x +154; serial: ira_priority +214, no_inline_small +42, relax +258, short_enums +488, strict_x +106. Adding the flag left out costs: SD `no_guess_branch` +86; serial `no_gcse` +72, `no_guess_branch` +30. One thing to read correctly: the tool flags `no_inline_small` as HURTS (+10 B) in the *all-on* row, but that row carries `no_guess_branch`, which is off; in the applied set it still pays (+72 SD, +42 serial). The flash margin of the SD image is the tight one (196 bytes against 30 720); a change of the code, not of the flags, is what will spend it. Size only: the applied set is unchanged, so the stack, cycle and machine checks of 2026-10-12 still stand; a release does not need them redone unless the set changes.

**Re-evaluated again 2026-10-31, the check before the first release: no change.** `flag_truth_table.py` was run on the code after `cmake/variant_modules.txt` and `Version.h`, both variants, all 2^7 = 128 combinations each, none FAILED (`SizeFlags-TruthTable-V1-sd.md` is byte-identical to the one of 2026-10-26: the SD image did not change; `-V1-serial.md` is new). The best subset of each table is again **the set already applied**, the global minimum: **SD 30 524 B (196 free); serial 28 776 B (1 944 free)**, equal to the images the build produces (`tools/analysis/build_size.sh`; the serial image is 10 B larger than the 28 766 B of 2026-10-27; `Version.h` came in between, the cause was not isolated; with the version 1.0.0 and no `-dev` suffix the serial image is **28 772 B**, 1 948 free, the SD image unchanged). The worst stack is unchanged (serial 405 B, SD 328 B, `stack_depth.py`). `no_gcse` still hurts the serial image (+104 B when dropped from the others' company), `no_guess_branch` both: they stay off. The tables of 2026-10-12 are kept for comparison.

## REQ-CoreLR-D-Build-0013 — The API documentation: the target `doc`, one documentation per image (2026-10-27, host-verified; Doxygen 1.15.0, also in CI since 2026-10-31)
<a id="REQ-CoreLR-D-Build-0013"></a>
Realizes no functional requirement of its own (none was added): it is a convenience for whoever reads the code, and it is bound by `REQ-CoreLR-F-Build-0002` and `-0004` — building an image never depends on it, and **no image changes by a byte** (measured: the two `.hex` and the sizes are the same before and after, see `docs/bringup/Bringup-Status.md`, 2026-10-27).
**One documentation per image (maintainer's decision, 2026-10-27: "like the firmware").** `cmake --build --preset host --target doc` (any preset: it needs Doxygen and no AVR compiler) makes both: `build/doxygen/serial/html/index.html` and `build/doxygen/sd/html/index.html` (`doc_serial` and `doc_sd` make one), a `build/doxygen/index.html` that links them, and in each directory the `doxygen-warnings.log` of that run, then prints the warnings by module. `CORELR_DOC_DIR` (default `build/doxygen`, git-ignored) is the same for every preset. Each run documents the code of its image as the compiler sees it: the code that exists in only one image appears only in that image's documentation (the SD browser in `sd`; `GCodeParser_ExecuteJog()` in `serial`; the modules `SDReader` in `sd` only and `Uart`, `SerialLink` in `serial` only), and `docs/doxygen/mainpage.md` says which one it is (`if serial` / `if sd` blocks, `ENABLED_SECTIONS`). (A first version, 2026-10-27 morning, documented both in one output; it mixed up what exists in which image and was replaced.)
**Contents.** A main page; one page per file of `firmware/src`, `firmware/config` and `firmware/app`, with its source; the `@defgroup` sections of `HwConfig.h` and `SwConfig.h` as two topics, *Hardware configuration* and *Software configuration* (`docs/doxygen/groups.dox` defines the parents, one `@ingroup` line in each `@defgroup` of the headers names its parent); search; include graphs and the **diagrams of the comments** when `dot` exists. The Doxyfile is `docs/doxygen/Doxyfile.in`, turned into `<build dir>/Doxyfile_<variant>` by `cmake/Doxygen.cmake` (`configure_file`: output directory, version, variant and its `CORELR_JOB_SOURCE` value, `HAVE_DOT`); Doxygen runs from the repository root, so the Doxyfile and the pages hold relative paths only. The targets re-run when a source, the template or a page changes, and clear `html/` first.
**What it does not do.** It is not part of `all` (no firmware target depends on it, `cmake --build --preset avr-default` never starts Doxygen); it reads the sources and writes nothing under them; the output is never committed; it fails on no warning (`WARN_AS_ERROR` is NO — the markup errors are checked by the tests below). It does not document `tests/` or `tools/`, produces no LaTeX/PDF/XML, and shows the **shipped configuration** only: the 48-bit arithmetic (the 64-bit code, e.g. `Motion_ISqrt()`, is absent) and no debug switch. **Without Doxygen** the configuration succeeds and says so; the targets stop with how to get it (`cmake/DocUnavailable.cmake`). **Without `dot`** (graphviz) the configuration says so and the targets stay usable: no include graph, the `dot` diagrams of the comments are skipped (Doxygen warns once for each; `tools/analysis/doc_warnings.py` counts them apart, as *no dot*, and the table says how to get the diagrams); nothing else is missing.
**The preprocessor, per image.** `ENABLE_PREPROCESSING = YES` is needed — with NO every documented `#define` is ignored (measured: 174 warnings, no configuration page). With `EXPAND_ONLY_PREDEF = YES` an `#if` expands only the macros of `PREDEFINED` and `EXPAND_AS_DEFINED`; anything else counts as 0. `PREDEFINED` gives the image exactly as `cmake/Firmware.cmake` gives it to the compiler (`CORELR_JOB_SOURCE=CORELR_JOB_SOURCE_<SERIAL|SD>`; the numbers behind the names are read in `SwConfig.h`, not copied) and the compiler's attributes, which Doxygen must not take for C: `PROGMEM=` (it hid every table in flash) and `"__attribute__(x)="` (added 2026-10-28: `} __attribute__((packed)) Entry_t;` made a structure called `__attribute__` and lost the name `Entry_t`, and the line `__attribute__((noinline))` before a definition detached the comment of 8 functions of `Motion.c`, which were listed as undocumented; `test_doxygen.py` checks that no such structure exists and that `Entry_t` has its page). `EXPAND_AS_DEFINED` lists the names of the images and the other selectors whose shipped value must hold — `CORELR_MATH*`, `CORELR_MENU_HOME`, `CORELR_Y_UP`, `CORELR_GCODE_Z`, `CALIBRATION_POSITION_RING`, `LCDJOYSTICKUI_PEN_GLYPHS`, `LCDJOYSTICKUI_HAS_SD`: they expand to their definition in the sources, so no default is copied into the Doxyfile and their own `#define` stays documented (predefining them hid it). **A new selector of `SwConfig.h` with a non-zero default, tested by `#if`, must be added to `EXPAND_AS_DEFINED`**, or the page shows its `#else` branch.
**The hardware chapter (maintainer's request, 2026-10-28).** `docs/doxygen/hardware.md`, a page *Hardware* linked from the main page (`subpage`), the same in both documentations except that the SD module and its picture are in `sd` only. It is a short text of ours, **not** the `docs/hardware/*.md` files (written for GitHub: links to `tools/` and `requirements/`, no Doxygen markup; they stay the full wiring guide, and the page says so): the pins are not repeated, they are those of the *Hardware configuration* topic (`HwConfig.h`), from which the wiring pictures are generated (`tools/generators/gen_wiring.py --verify`). It shows, with `image html`, the pictures of `docs/hardware/images/` (`IMAGE_PATH` lists `images/` and `images/wiring/`: Doxygen does not look into subdirectories): `overview`, `motors`, `pen_servo`, `joystick`, `lcd_i2c`, `sd_card` (sd only), and the two generated by the project's tools, `Geometry` and `Tension` (the geometry's numbers are an example, D = 1000 mm, **not the maintainer's machine**, and the page says so). `nano_led.svg` (a style reference, not the machine) is left out. **Licence:** the wiring pictures embed Fritzing parts and are **CC BY-SA 3.0**, not GPLv3 (`docs/hardware/images/wiring/README.md`, `third_party/fritzing-parts/PROVENANCE.md`); the page ends with *Credits and licences*: Fritzing, the licence and its URL, each part's author, and what the project drew itself. Each SVG keeps its own credit in its metadata, and `test_doxygen.py` fails if a copied wiring picture has lost it, if the page does not name the licence and every author, or if a picture is not copied or not shown. The pictures are dependencies of the target (`cmake/Doxygen.cmake`: a regenerated picture re-runs it). ## REQ-CoreLR-D-Build-0020 — The version: `firmware/config/Version.h`, read by everything, checked against the tag (maintainer's decision, 2026-10-31, host-verified)
<a id="REQ-CoreLR-D-Build-0020"></a>
Realizes `REQ-CoreLR-F-Build-0007`. **One file**, `firmware/config/Version.h`: `CORELR_VERSION_MAJOR`, `_MINOR`, `_PATCH` and `CORELR_VERSION_SUFFIX` (`"-dev"` between two releases, `""` on the commit that carries the tag), and `CORELR_VERSION_STRING`, the string literal made of them (`<x.y.z>-dev` between two releases, `<x.y.z>` on a release). A C header because every consumer can read one: the firmware (`$I`), the exported sketch and the IDE build (they copy `firmware/config/`), CMake and the check tool (they read the four lines as text: `#define NAME value`, one per line, which the tool enforces). The decision between a header, `CMakeLists.txt` and a `VERSION` file was the maintainer's (the IDE build cannot read CMake; a text file would need a generated header).

**Consumers.** `CMakeLists.txt` sets `CORELR_VERSION_NUMBER` (`<x.y.z>`, for `project(VERSION)`) and `CORELR_VERSION` (`<x.y.z>-dev`, or `<x.y.z>` on a release: the names of the release files, the documentation and its package); its former literal `set(CORELR_VERSION "0.1.0")` is gone. The `release` workflow runs `tools/analysis/check_version.py --tag "$GITHUB_REF_NAME" --sources`: the tag must be `v` + the numbers **and** the suffix must be empty, and the version must be written nowhere else. `$I` answers `[VER:1.1h.20261011:CoreLR <version>]`: the **date stays** (`FW-13`, `P15` of the protocol: a sender may parse it; Candle and grbl put free text after the second colon), the name and the version go in that free text. This is an extension of the reply, not a change of the contract; the host side owns the text of `SerialProtocol.md` and is told (`docs/design-notes/SerialProtocol-review-2026-10-29.md`, section G). Cost: **+10 bytes of flash in the serial image** (`CoreLR ` and the version, in a string that was already there); the SD image does not have `$I` and is unchanged.

**What the version is on any branch.** The last release plus `-dev`, never a hash: a hash in the image would make two builds of identical sources differ, and the `.hex` files are compared byte for byte (the proof, throughout this project, that a change touched no image). A hash may go in the build report, outside the image (not done). The commit that releases empties the suffix and is the one tagged; the next commit puts `-dev` back (to do by hand, or by the release checklist).

**Checks.** `ctest`: `version` (`tests/tools/test_check_version.py --cmake-version ${CORELR_VERSION}`): the tool on fabricated trees, one defect at a time (`tests/mutation/mutants/check_version.txt`, 30 mutants, all caught), and on this repository -- `Version.h` readable, the version written nowhere else, and equal to the one CMake read (two parsers of one file must agree). `tests/host/test_seriallink.c` checks the reply of `$I` with the macro.

**Not done.** The version on the LCD's start-up screen (the SD image has no `$I`, so its only way to say its version would be the screen: costs flash, of which it has 196 bytes; to decide). A hash in the build report. Putting `-dev` back after a tag is by hand.
